# Saunf — Architecture

Saunf is an internal task-management platform for a single organisation. It is a
Next.js App Router application backed by Supabase (PostgreSQL, Auth, Storage).

## 1. Stack (versions verified at development time, Oct 2026)

| Concern        | Choice                                                         |
| -------------- | -------------------------------------------------------------- |
| Framework      | Next.js 16.4.2 (App Router, Cache Components, `proxy.ts`)      |
| UI runtime     | React 19.3                                                     |
| Language       | TypeScript 5, `strict: true`                                   |
| Styling        | Tailwind CSS 4 (CSS-first config, tokens in `globals.css`)     |
| Components     | shadcn/ui-style components (source in `src/components/ui`) on the `radix-ui` package |
| Icons          | lucide-react                                                   |
| Data / Auth    | Supabase Postgres + Supabase Auth via `@supabase/ssr` 0.12     |
| Files          | Supabase Storage (private bucket `task-attachments`)           |
| Validation     | Zod 4 (shared schemas in `src/lib/validation`)                 |
| Forms          | React Hook Form + `@hookform/resolvers`                        |
| Dates          | date-fns 4 + `@date-fns/tz`                                    |
| Drag and drop  | dnd-kit                                                        |
| Charts         | Recharts 3                                                     |
| Scheduler      | `pg_cron` inside Postgres (due-soon / overdue reminders)       |
| Tests          | Vitest (unit + RLS integration against local Supabase), Playwright (E2E) |

## 2. High-level design

```
Browser ──► proxy.ts (refresh Supabase session cookie, redirect anonymous users)
        ──► Server Components (read with the user's JWT → RLS-filtered)
        ──► Server Actions (validate with Zod → call Postgres with the user's JWT)
        ──► Supabase Storage (direct upload with the user's JWT, storage RLS)

Postgres
  ├─ RLS on every table (source of truth for authorisation)
  ├─ SECURITY DEFINER helper functions (permission predicates, no RLS recursion)
  ├─ BEFORE triggers  (derived fields + field-level permission guard)
  ├─ AFTER triggers   (append-only activity log, assignment history, notifications)
  └─ pg_cron job      (due-soon / overdue notifications every 15 min)
```

Key decisions:

1. **Postgres is the authorisation boundary.** Every read and write from the app
   uses the signed-in user's JWT, so RLS applies. The service-role key is used
   only in a handful of server-only admin operations that Supabase Auth requires
   it for (inviting / creating / banning auth users). It lives in
   `src/lib/supabase/admin.ts`, which imports `server-only`.
2. **Server Actions re-check everything.** They derive the actor from the session
   (`auth.uid()` inside Postgres), never from the request body, validate input with
   Zod, and rely on RLS + triggers as the final gate. UI hiding is cosmetic only.
3. **Audit is produced by the database.** Activity events, assignment history and
   notifications are written by `SECURITY DEFINER` triggers, so they can't be
   skipped by a client that talks to PostgREST directly, and ordinary users have
   no INSERT/UPDATE/DELETE rights on those tables. An extra trigger makes
   `activity_events` and `task_assignments` append-only even for the table owner,
   unless a retention job explicitly opts in.
4. **Multi-write operations are single Postgres functions.** `create_task` and
   `update_task` insert/update the task, its labels and collaborators in one
   transaction. They are `SECURITY INVOKER`, so RLS still applies inside them.
5. **Task keys are concurrency-safe.** `SAU-00001` comes from a per-workspace
   counter incremented with `UPDATE … RETURNING` inside the insert trigger; the
   row lock serialises concurrent inserts. A unique constraint backs it up.
6. **One workspace today, modelled explicitly.** Every private row carries
   `workspace_id`, and membership (`workspace_members`) carries role, department
   and active flag. A user is a member of at most one workspace in this release;
   the schema allows more.
7. **Cache Components.** All application data is per-user and read with cookies,
   so pages render dynamic content inside `<Suspense>` (via `loading.tsx` and
   explicit boundaries). Nothing user-specific is placed in `use cache`.
   Mutations call `refresh()`/`revalidatePath()` so the UI reflects the database.
8. **Timestamps.** All `timestamptz` columns are generated by Postgres (`now()`)
   and stored in UTC. The UI formats them in the viewer's browser timezone; the
   workspace timezone setting is used for day boundaries in reminders and
   "due today" calculations on the server.

## 4. Database schema

See `supabase/migrations/*.sql` for the authoritative definition.

| Table                 | Purpose |
| --------------------- | ------- |
| `workspaces`          | Organisation; `task_prefix`, `task_counter` |
| `workspace_settings`  | Policies: creation/assignment/visibility, defaults, timezone, reminders, retention |
| `profiles`            | 1:1 with `auth.users`; name, email, title, avatar, notification prefs |
| `workspace_members`   | user ↔ workspace with `role`, `department_id`, `is_active` |
| `departments`         | name, manager |
| `invitations`         | pending invites (email, role, department, expiry, status) |
| `projects`            | name, description, owner, status, dates, `is_private` |
| `project_members`     | user ↔ project (`lead`/`member`) |
| `tasks`               | current task state (one row per task) |
| `task_collaborators`  | additional people on a task |
| `task_assignments`    | complete, append-only assignment history |
| `labels`, `task_labels` | workspace labels and their tasks |
| `task_dependencies`   | "task A is blocked by task B" edges |
| `task_comments`       | comments with soft delete and mentions |
| `task_attachments`    | metadata for files in Storage |
| `activity_events`     | append-only audit log (task, project and admin events) |
| `notifications`       | in-app notifications, read state |

Status (`todo`, `in_progress`, `in_review`, `done`) and priority (`low`, `medium`,
`high`, `urgent`) are Postgres enums. "Blocked" is a separate flag
(`is_blocked` + `blocker_description`) so blocked work keeps its status column.

Separate timestamp concepts on `tasks`: `created_at` (immutable), `assigned_at`
(latest assignment), `start_date`, `due_date` + optional `due_time`,
`completed_at`, `archived_at`, `updated_at`.

## 5. Notifications and reminders

* Assignment, reassignment, comment, mention, completion, reopen and
  "review requested" (status → In review) notifications are created by triggers.
  Minor field edits do not notify.
* Due-soon and overdue notifications are created by `generate_due_notifications()`,
  scheduled every 15 minutes by `pg_cron` (migration `…_cron.sql`). A unique index
  makes it idempotent (one due-soon and one overdue notice per task per due date).
* Email: notification emails are optional. `/api/cron/email-notifications` sends
  unsent notifications through Resend when `RESEND_API_KEY` and `CRON_SECRET` are
  configured; otherwise it reports that email is not configured. Auth emails
  (invite, password reset) are sent by Supabase Auth's SMTP configuration.

See `docs/SECURITY.md` for the permission matrix and RLS model.
